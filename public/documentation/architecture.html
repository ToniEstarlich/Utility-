Architecture

Small tools.
Clear structure.

Utility is organized so that every tool can contain its own interface, logic, styles, and Python processing without becoming dependent on a large central system.

How a tool works

What each layer does

HTML The structure and visible interface of the tool.
JavaScript The interaction and client-side behavior.
CSS The visual design, layout, spacing, and states.
Python The heavier processing and backend logic.

Tool-based architecture

Each Utility tool owns its own files. This keeps tools understandable, independent, and easier to develop or replace. 

Utility/
└── src/
    └── app/
        └── tools/
            ├── pdf/
            │   ├── compress-pdf/
            │   │   ├── page.tsx
            │   │   ├── CompressPdf.tsx

            │   │   └── backend/
            │   │       ├── main.py
            │   │       └── compress.py
            │   │
            │   └── merge-pdf/
            │       └── backend/
            │           ├── main.py
            │           └── merge.py
            │
            └── images/
                └── compress-image/
                    └── backend/
                        ├── main.py
                        └── compress.py

Simple principle

A developer should be able to open a tool folder and immediately understand everything that belongs to that tool.

The architecture stays modular at the tool level while the production backend can still run as a single FastAPI service when Utility is deployed.
